YAML and the Future

YAML usage is growing steadily in the computing industry; both in general programming and especially in cloud computing. This is most likely due to:

  • YAML's use of minimal syntax (non-tech people can read/understand it)
  • Programming language agnostic (works about the same in any environment)
  • Simple API (just Load and sometimes Dump)
  • Interchangeable with JSON (YAML is a syntax/model superset of JSON)

Given its increasingly important place in production computing, it becomes more and more critical that the YAML language and its tools are rock solid.

Unfortunately this isn't the case. YAML is a very complex language, with a 5-layer processing stack, and a long list of edge cases. YAML was designed to simultaneously look and feel simple, while handling all the data serialization needs for all programming languages. In reality, the language was created by a handful of people in a very grassroots manner, and spread organically across the computing landscape. The efforts were well intended but after almost 10 years, the creators mostly called it quits and moved on. Many things got left in an unfinished state.

YAML's problems fall roughly into 3 categories: "syntax", "schema" and "tools". The problems include:

  • No two YAML frameworks work the same
  • No YAML implementation correctly implements the YAML spec (1.0, 1.1, 1.2)
  • The 1.2 spec has dozens of flaws (implementation can be maddening)
  • Needs a definitive test suite (to match and cross reference the spec)
  • Most implementations (including libyaml) are still at 1.1
  • libyaml (shared library) is written in C (vulnerabilities arise)
  • No programatic/templating features (all serious users make their own)
  • No YAML doc stands alone semantically (a schema is required)
  • There is no YAML schema language yet (each framework has a hardcoded schema)
  • Using YAML in statically typed languages (like Go) is too hard
  • Misunderstood (very few people have knowledge of the YAML processing stack)
  • There are no books written about YAML

More simply put, YAML is a (extremely useful) house of cards, that is growing in use every day. It needs and deserves to be seen in a more critical light than just a config file format.

Fortunately, every one of the listed problems is solvable. Now YAML has many years of real world usage to learn from and guide its future. Here are some of the envisioned, planned, or in-progress solutions:

  • YAML 1.3 is in progress, with these goals:
    • Fully replace 1.2, 1.1 and 1.0
    • Add simple/powerful "annotations" and "expansions" features (think templating)
    • Remove unused 1.2 edge-cases (that often cripple implementation)
    • Every spec detail has one or more YAML Test Suite cases (empirical compliance)
    • Achieve real inter-language/framework compatibility
    • Encourage written schemas for almost every kind of use
  • Creation of SchemaType(.org) as the Schema Language for YAML (and thus JSON)
    • Focused on full-stack code generation (code, docs, sql, tests, wire, editors, ...)
    • Goes far beyond data validation
    • A schema-aware loader makes Go usage as simple as Python (and Python as rigorous as Go)
  • Write new 1.3 reference implementation (in something like Go or Rust)
    • Support a schema-aware Load API
    • Supports new annotation features
    • Should produce a libyaml shared lib (for use in other languages)
  • Write a book on YAML that explores its depth in detail

Work is ongoing by a few people in their spare time, but that is neither achievable or responsible. It's time for YAML to grow up and get serious. I'm confident that with the backing of the right people, I can guide the YAML project into a promising future.
